## How it maps to the Claude Code adapter

| Concern | Claude Code | Codex |
|---|---|---|
| Rules | `CLAUDE.md` imports `AGENTS.md` | `AGENTS.md` read natively (`project_doc_max_bytes`) |
| Deny reads | `permissions.deny` globs | `[permissions.research-harness.filesystem.":workspace_roots"]` `"…" = "deny"` |
| No network / confined writes | sandbox + settings | `sandbox_mode = "workspace-write"`, `network_access = false` |
| Agent env | `env` block (`RH_AGENT_SESSION`, `RH_HOST`) | `[shell_environment_policy.set]` |
| Secrets out of env | — | `ignore_default_excludes = false` keeps `*KEY*`/`*SECRET*`/`*TOKEN*` out |

Both hosts share the one host-neutral `AGENTS.md`, so the rules are identical
(NFR-13).

## Deny rules are defence in depth, not the guarantee

Codex **named permission profiles are beta and Codex ≤ 0.137.0 ignores them**.
The binding guarantee that holdout / secrets / private files never leave the
harness is the in-code forbidden-path check in `rh repo check` and `rh-dev
check` (H1, H8, NFR-11), which runs identically on every host. The Codex deny
globs here simply add a second layer on hosts that honour them.

## Parity (NFR-13, T42)

`rh` is runtime-neutral: its JSON envelopes depend only on the repository state,
not on `RH_HOST`. The same fixture therefore yields the same CLI results under
Claude Code and Codex (see `tests/unit/host/test_codex.py::test_cli_output_is_host_neutral`).
