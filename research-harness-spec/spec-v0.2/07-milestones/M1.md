### M1-02 Core utilities

**Goal.** Shared primitives every module uses: IDs, hashing, time, safe paths, artifact refs, envelope, errors and exit codes; plus the import and dependency guards.

**Requirements / tests.** 02 §1, 03 §1; NFR-07, NFR-14; **T15 (imports)**; T24 for `checksums.py`.

**Depends on.** M1-01.

**Reuse.** AutoResearchClaw `researchclaw/hitl/checksums.py` (registry #21; pinned `be4ba47`, MIT) — **copy + adapt**. Resolve the full 40-char SHA of `be4ba47` upstream and record it. Keep the original header; add `Adapted from …` with the list of changes (canonical JSON, CRLF normalization, BOM stripping per 02 §1.3).

**Files.** `research_harness/core/{ids.py, ulid.py, hashing.py, clock.py, paths.py, refs.py, envelope.py, errors.py}`, `research_harness/i18n/{__init__.py, uk.yaml, en.yaml}`, `harness/third_party/autoresearchclaw/checksums.py` (original, for diffing) or the adapted code inside `core/hashing.py` — either way with an adoption record; `research_harness_dev/guards.py`; tests in `tests/unit/core/`.

**Steps.**
1. `ulid.py`: monotonic ULID generator, stdlib only.
2. `ids.py`: allocators and validators for every format in 02 §1.2; Crockford base32 unit IDs with collision retry.
3. `hashing.py`: canonical JSON hash, text-file hash (BOM strip, CRLF/CR → LF), binary hash, streaming for large files.
4. `clock.py`: injectable now/today (UTC); `--clock` accepted only when `RH_TEST_MODE=1`.
5. `paths.py`: NFC normalization, forbidden-character removal, 60-char title trim at a word boundary, relative-path validation (reject absolute and `..`), NFC-aware lookup.
6. `refs.py`: parse and format artifact refs (02 §1.4).
7. `envelope.py`, `errors.py`: envelope builder (schema-validated after M1-03) with `lang` and `message`; exception classes mapped to exit codes 2/3/4/5, each carrying a message key, never a hard-coded sentence.
7a. `i18n`: `t(key, lang, **params)` over `uk.yaml` / `en.yaml`; language resolution `--lang` → `RH_LANG` → `_author/profile.yaml ui_language` → `uk` (02 §1.6); missing key in one language falls back to the other and logs a warning; `rh-dev check` step fails if any key exists in only one catalog or if a user-facing string literal is passed to the envelope instead of a key (AST check on `envelope.message=`/`why=`).
8. `guards.py` + `rh-dev check` step: (a) AST scan — `research_harness` must not import `anthropic`, `openai`, `litellm`, `google.generativeai`, `langchain*`, `fitz`, `pymupdf`, `paperqa`, nor anything under `harness/host/`; (b) lockfile scan — fail if `pymupdf`, `paper-qa-pymupdf` or `paper-qa` appear.
9. Adoption record for `checksums.py` in `third_party/manifest.json` and `THIRD_PARTY_NOTICES.md`; `rh-dev check` step that validates records (02 §13) and that their acceptance tests exist.

**Verify.**
```
uv run pytest tests/unit/core -q
uv run rh-dev check
```

**DoD.** Tests cover: Cyrillic titles and NFD input produce NFC names; `Назва: «тест» / ?` sanitizes as specified; CRLF and LF versions of a file hash equal; BOM ignored; canonical JSON hash independent of key order; `..` and absolute paths rejected; `rh --lang en version` and `rh --lang uk version` return the same JSON except `lang` and `message`; a key missing from `en.yaml` makes `rh-dev check` fail. Guard test: a temporary module importing `anthropic` inside `research_harness` makes `rh-dev check` fail (T15 imports). Adoption record valid (T24).

### M1-04 State store, commit protocol, recovery

**Goal.** Atomic snapshots, single writer, idempotent operations, explicit recovery — the backbone of FR-11 and NFR-01.

**Requirements / tests.** 02 §5; ADR-002; FR-11, NFR-01; **T10**.

**Depends on.** M1-02, M1-03.

**Reuse.** AutoResearchClaw `researchclaw/pipeline/runner.py` functions `_write_checkpoint`, `_write_heartbeat`, `read_checkpoint`, `resume_from_checkpoint` (registry #20) and `researchclaw/pipeline/contracts.py` `StageContract` (#19) — **adapt functions, not the file** (runner is 1 864 lines). Pinned `be4ba47`, MIT. One adoption record each.

**Files.** `research_harness/state/{store.py, lock.py, operation.py, snapshot.py, events.py, recovery.py, dirty.py, contracts.py}`, `tests/unit/state/`, `tests/fault/test_commit_interrupts.py`, `research_harness_dev/fixtures/f5b.py` (part: object states with checkpoints).

**Steps.**
1. `lock.py`: exclusive create, holder metadata, `LockHeld` → exit 4; stale lock reported, never auto-removed.
2. `operation.py`: context manager implementing the nine steps of 02 §5.3 with idempotency keys; the write set is declared up front.
3. `snapshot.py`: manifest build, blob store (`objects/<sha256>`), `stored=false` for gitignored paths, `manifest_sha256`, tags.
4. `events.py`: append with fsync; reader that isolates a truncated tail.
5. `recovery.py`: the table in 02 §5.5, run at command start; `rh resume` exposes it explicitly, including stale-lock recovery after confirming the holder PID is gone.
6. `dirty.py`: dirty set vs `CURRENT`; overlap with an operation's write set → exit 3 with `next_action: rh checkpoint`.
7. `contracts.py`: `StageContract` dataclass (inputs, outputs, DoD checks, gate, error codes, max_retries) adapted from #19; no stage logic yet.
8. CLI: `rh checkpoint --by human|agent [--request TEXT] [--units U…] [--message]` (02 §5.6: `--by agent` without `--request` → exit 2; request stored in `operation.request`; `--units` limits the snapshot's dirty set to those units and reports other dirty files), `rh resume`, `rh history` (shows producer and, for agent edits, the request).
8a. Before any mutating command, an un-checkpointed dirty set outside the write set is recorded as a snapshot with producer `unattributed` (02 §5.6) and reported in the envelope.
9. Fault injection: hook `RH_FAULT_AT=<step>` (honoured only with `RH_TEST_MODE=1`) that raises or calls `os._exit` at each of the nine steps; subprocess tests run an operation, kill it at each step, then run recovery.

**Verify.**
```
uv run pytest tests/unit/state tests/fault -q
uv run rh-dev check
```

**DoD (T10).** For each of the nine kill points and for a truncated `events.jsonl`: after recovery either the old or the new snapshot is current; the working tree equals `CURRENT`; no committed snapshot lacks a blob; repeating the same command does not create a second snapshot; the truncated tail is in `quarantine/` and reported as a finding. A concurrent second writer gets exit 4. `rh checkpoint --by agent` without `--request` → exit 2; with it, `rh history` shows the request text; an author edit followed by another command without checkpoint ends up in an `unattributed` snapshot, never lost.

### M1-05 Freshness and invalidation

**Goal.** Computed staleness over the dependency graph; approvals bound to snapshots.

**Requirements / tests.** 02 §6; FR-10; **T09**.

**Depends on.** M1-04.

**Reuse.** None.

**Files.** `research_harness/state/freshness.py`, `research_harness/validate/freshness_checks.py`, `tests/unit/state/test_freshness.py`, `research_harness_dev/fixtures/f5b.py` (part: dependency graphs).

**Steps.**
1. Build the graph from every record with `inputs` / `dependencies` / `evidence` in the current snapshot.
2. Compute `stale` transitively; expose `rh validate --scope freshness` and a library API used by `status`.
3. Approval validity: valid only if `target.manifest_sha256` equals the current snapshot's, or, when `target.refs` is set, if every listed ref still has its recorded hash.
4. A rule-pack version change marks dependent check runs stale.

**Verify.**
```

Unrelated artifacts stay `current`.

**Requirements / tests.** 02 §4.2; 03 §2.1, §3; FR-28 (status), FR-41 (start, continue), FR-33 (autonomy stored; enforcement in M3); **T29a (status), T44 (start / continue)**.

**Depends on.** M1-05, M1-07, M1-09, M1-10.

**Reuse.** None (uses `StageContract` from M1-04).

**Files.** `research_harness/lifecycle/{stages.py, article_stages.yaml, thesis_stages.yaml, routing.py, status.py}`, CLI handlers, `tests/integration/test_status.py`, `tests/integration/test_routing.py`, `research_harness_dev/fixtures/f5b.py` (part: objects at A0, A2, A12 with an open G3 request, A14, A16).

**Steps.**
1. Stage definitions as data: ID, name, inputs, outputs, DoD check IDs, gate, conditions (A5 `not_applicable` when `participants=false`; A16 `waiting`).
2. Stage transitions only through `rh`; `completed` requires the DoD checks to pass; `blocked` requires reason and next action.
3. `rh start`: no matching object → create it (M1-06) with the unit-tree skeleton for its kind (article: empty `structure.yaml`; thesis: introduction, conclusions, references), set A0 active, return the intake questions. A title matching an existing object → exit 2 with candidates (the single clarification of FR-41). `--mode revise|respond_to_reviewers` → exit 2 "available in M3".
4. `rh continue`: recovery report + status + next action; no content change.
5. `rh status` per 03 §3; text rendering in the output language (Ukrainian by default, `--lang en`); stage and gate names come from the catalogs, IDs stay as they are (`A2`, `G0`).
6. `SubmissionRecord` / `PublicationRecord` are M3; status shows A13–A16 states from fixtures only.

**Verify.**
```
uv run rh-dev fixtures generate F5b
uv run pytest tests/integration/test_status.py tests/integration/test_routing.py -q
```

**DoD.** T29a (M1 part): for each F5b state the status shows the right current stage, gates, blockers, unknowns with consequences, dirty files and exactly one next action. T44 (M1 part): `start` in an empty workspace creates an object and returns intake questions; `start` with an ambiguous title returns candidates (exit 2); `continue` on an object with a quarantined operation reports it and the next action without changing files.

### M1-14 Claude Code adapter v0 and `AGENTS.md`

**Goal.** The author can work through Claude Code: start an object, run intake in conversation, see status, continue — with holdout and private paths denied and agent shells marked.

**Requirements / tests.** ADR-001 rev.2 p.2–5; ASR-03; H1, H12; `05-eval-base.md` §2 p.5.

**Depends on.** M1-11.

**Reuse.** None in M1 (OPM and K-Dense skills are adopted in M2 with records).

**Files.** `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json`, `harness/host/claude-code/` (skills or commands for `start`, `continue`, `status`, `intake` — mechanism per current Claude Code docs), `harness/host/claude-code/README.md`, `tests/unit/host/test_claude_config.py`.

**Steps.**
1. Read the current Claude Code docs for: memory-file import syntax, skills, slash commands, subagents, `permissions.deny`, environment variables for tool shells, hooks. Cite URLs and dates in the PR.
2. `AGENTS.md` (English — agent instructions, 02 §1.6; host-neutral):
   - purpose; hard rules H1–H15 rewritten as agent behaviour;
   - **languages**: talk to the author in the language he uses; write manuscript text in the object's language; pass `--lang` matching the conversation when calling `rh` with `--format text`;
   - **edits** (H13, 02 §5.6): controlled files only through `rh`; content files only when the author asked; diff first for non-trivial changes; right after the edit `rh checkpoint --by agent --request "<author's words>"`; never edit locked units;
   - **gates** (H14): never run `rh gate record`; when `next_actions` contains an author action, send the author a message with (1) what is being decided, in one or two sentences, (2) the briefing path and the 3–5 most important things to check from it, (3) the exact command in a code block, (4) that it must be run in his own terminal window, (5) what `rh` will ask and what happens after approve / reject; then wait;
   - intake: ask questions in the conversation language, one block at a time, using `help` texts when the author hesitates; write answers via `rh intake answer`;
   - how to read the envelope and act on `next_actions`; where the spec lives.
3. `CLAUDE.md`: imports `AGENTS.md` only.
4. `.claude/settings.json`: deny reading and searching `**/holdout/**`, `.env`, `*.local.yaml`; set `RH_AGENT_SESSION=1` and `RH_HOST=claude-code` for agent shells if the host supports env configuration (otherwise document the limitation; the TTY rule still applies). Find out from the docs and by test whether commands the author runs from inside Claude Code (e.g. its shell-command mode) inherit this environment or a TTY; write the result in `harness/host/claude-code/README.md` (Ukrainian) as plain instructions: "where to run `rh gate record`" — normally a separate terminal window.
5. Entry skills or commands `start`, `continue`, `status`, `intake`: thin wrappers that call `rh` and present results; no logic beyond formatting.
6. Test: config files parse; deny patterns include `**/holdout/**`; `AGENTS.md` mentions every hard-rule ID H1–H15.

**Verify.**

```

**DoD.** The PR contains a session excerpt (in Ukrainian) showing start → intake → the agent's G0 message with all five elements of step 2 "gates" → the author records G0 in his own terminal → continue; the holdout read was denied; the agent created no approval; asked to "shorten the introduction", the agent showed a diff, applied it after OK and checkpointed with `--request`.
