# Етап 0 — план, рішення і брифи для окремих чатів

Дата: 2026-10-27. Цей документ — точка входу для кожного чату етапу 0. Кожен крок виконується в окремому чаті проєкту; чат-координатор збирає підсумки.

## Як працювати з цим документом

1. Новий чат у проєкті починається фразою: «Виконуємо крок X етапу 0 за `research-harness-spec/stage-0/00-stage0-plan.md`».
2. Чат читає цей файл, вхідні документи свого кроку і працює лише в межах кроку.
3. Результат кроку — документ у проєкті за вказаним шляхом. Рішення автора записуються в розділ «Рішення» цього документа результату з датою.
4. Наприкінці чат оновлює статус кроку в таблиці нижче (через перезапис цього файлу) і перелічує відкриті питання для координатора.
5. Підсумки зводяться в чаті-координаторі.

## Брифи

### Крок 1. Аналіз наявних матеріалів

**Мета:** одне зведення того, що вже є, і реєстр суперечностей між spec v0.1 (2026-10-13), addendum (2026-10-20) і рішеннями вище.
**Вхід:** усі файли `research-harness-spec/`; інші матеріали автора, якщо додасть.
**Вихід:** таблиця «тема → що каже v0.1 → що каже addendum → що вирішено зараз → суперечність / прогалина → пропозиція».
**DoD:** кожна суперечність має пропозицію; позначено, які пункти addendum переходять у MVP, а які в LATER.
**Межі:** не переписувати старі файли спеки.

### Крок 2.5. Життєвий цикл статті та дисертації

**Мета:** чітко описати, як система працює на кожному етапі створення статті і дисертації, де потрібна людина, а що робить система автоматично, яка структура кожного артефакту, як виглядає робота користувача.
**Вхід:** `03-workflow.md`, `06-contracts.md`, addendum §5–8, документ 12 (що з аналогів покриває який етап).
**Перше питання чату:** перший реальний кейс (див. відкриті питання).
**Вихід:**
- Життєвий цикл статті: етапи, входи / виходи, артефакти, gates, повернення назад.
- Окремий життєвий цикл дисертації (не «довга стаття»): горизонт у роки, керівник, вимоги установи, статті як складові, розділи як studies.
- Режими create / revise / extend / respond_to_reviewers.
- Для кожного етапу: що робить система, що перевіряє автоматично, що вирішує людина, які ролі задіяні.
- Опис роботи користувача: типові сесії в Claude Code / Codex, команди, що бачить у status.
- Зіставлення етапів із рядками реєстру reuse і вибір 5–8 K-Dense skills.
**DoD:** кожен етап має вхід, вихід, тип перевірки (детермінована / семантична / людська) і власника рішення; автор погодив цикл.

### Крок 3. ADR / ASR / FR / NFR

**Мета:** оновлені вимоги v0.2 на основі кроків 1 і 2.5.
**Вхід:** `04-requirements.md`, `05-architecture.md`, addendum §11, результати кроків 1 і 2.5.
**Вихід:** FR / NFR / ASR з пріоритетами MUST / SHOULD / LATER і прив'язкою до тестів; ADR на кожне рішення з таблиці вище та нові.
**DoD:** кожна FR має acceptance test; кожен ADR має контекст, рішення, альтернативи, наслідки.

### Крок 4. Специфікація для агента-реалізатора

**Мета:** покрокова інструкція, за якою агент у Claude Code / Codex реалізує harness і валідує кожен крок.
**Вхід:** результати кроків 2.5 і 3 (`03-requirements-v0.2.md` v0.2.1 і всі ADR, зокрема ADR-019 про великі документи і ADR-020 про лабораторію; `06-research-agent.md`), документ 12, критерії виходу milestones M1–M6 — `05-eval-base.md` §8. Де `02-lifecycle.md` суперечить v0.2.1 (ID-зв'язки study ↔ article ↔ thesis, шлях `projects/<stable-id>-<slug>`, M4 = ML), чинна v0.2.1.
**Вихід:** набір файлів spec v0.2 (структуру обирає чат); для кожного модуля — контракт, файли reuse з origin / SHA / ліцензією, тести, порядок реалізації.
**DoD:** агент може стартувати без додаткових пояснень; кожен крок реалізації має перевірку.
**Межі:** не читати `research-harness-spec/holdout/` (закритий набір оцінювання).
**Примітка:** найбільше дискусій з автором — тут.

### Крок 5. База оцінювання якості

**Мета:** набір питань, завдань і еталонних відповідей, щоб міряти якість системи на кожному етапі розробки і після неї.
**Вхід:** `08-validation.md` (F1–F3, T01–T16), §5 документа 12 (негативні кейси), вимоги кроку 3.
**Вихід:** каталог задач з еталонною розміткою, метриками і способом запуску; поділ на робочий набір і закритий holdout.
**DoD:** кожна MUST-вимога покрита хоча б одним кейсом; є негативні кейси (relevance ≠ support, підміна чисел, неповне покриття).
