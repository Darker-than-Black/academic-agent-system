## 1. Мета і принципи

Мета — міряти якість harness на кожному milestone і після нього, а не лише наприкінці. [С] ADR-007: milestone не завершений без проходження свого набору тестів.

1. **Спочатку збереження доказів, потім стиль.** [С] `08-validation`. Тести на вигадані джерела, підміну чисел і хибний PASS мають вищий пріоритет, ніж якість тексту.
2. **Детерміноване — 100%.** Детерміновані перевірки (CLI, без LLM) мають проходити повністю на кожному milestone. Порогів «майже» для них немає.
3. **Семантичне — з розміром вибірки і довірчим інтервалом.** Значення метрики без n і CI не приймається як результат.
4. **Holdout закритий.** Агент-реалізатор ніколи не бачить ні його вмісту, ні поелементних помилок на ньому (§2).
5. **Негативні результати зберігаються.** [С] `08-validation`: якщо B не кращий за A — спрощуємо harness.
6. **Еталон holdout ставить людина.** Holdout F4-H розмічає автор без участі агентів; робочий набір F4-W — чернетка агента, перевірка і правки автора [Р].

## 2. Набори: робочий і holdout

| Набір | Що це | Хто бачить | Де лежить | Для чого |
|---|---|---|---|---|
| **W — робочий** | Тренувальні задачі з еталоном | Агент-реалізатор, чати спеки, автор | Репо: `harness/evals/` | Налаштування промптів, skills, перевірок; щоденний прогін |
| **H — holdout** | Екзаменаційні задачі з еталоном | Лише автор; агент не бачить ні вмісту, ні поелементних результатів | Документи Project, лише в зашифрованому вигляді (§2, технічний захист) [Р]; у репо — лише `evals/holdout.lock.json` з hash | Чесний вимір якості на gate milestone |

**Що потрапляє в holdout:** лише семантичні задачі, де модель може «підігнатися» під відповіді: витяг claims, support verdict, виявлення seeded defects у тексті, integration review, вірність стилю. Детерміновані тести (схеми, hashes, resume, PR-перевірки, rule packs) holdout не потребують — їх неможливо «вивчити», вони або проходять, або ні.

**Правила holdout [П]:**
1. Підтема F4-H обирається автором і в репо не записується.
2. Прогін: автор копіює H у тимчасову теку поза репо, запускає `rh eval run --suite holdout`, у репо комітить лише агреговані метрики (n, значення, CI, hash набору, model ID, дата) у `evals/results/holdout-log.jsonl`.
3. Поелементні результати H лишаються поза репо. Якщо агент побачить, на якому claim помилився, holdout перестає бути закритим.
4. Якщо H скомпрометовано (вміст потрапив у репо чи промпт) — H замінюється новим пакетом, а попередні метрики H позначаються як `compromised`.
5. **Технічний захист** [Р] — автор обрав Project + технічну заборону. Заборонити чатам claude.ai шукати по документах Project технічно неможливо, тому захист — шифрування плюс блокування в репо:

| Шар | Механізм | Від чого захищає |
|---|---|---|
| Project | H зберігається лише як зашифрований архів `research-harness-spec/holdout/F4-H.age` (ASCII armor; `age` або `gpg`). Ключ — лише в автора: не в Project, не в репо, не в memory | Чат знайде файл пошуком, але побачить лише шифротекст |
| Репо: доступ агента | H у репо відсутній. Заборона читання шляхів `**/holdout/**` у налаштуваннях хоста (`.claude/settings.json` → `permissions.deny`; аналог для Codex). Точний синтаксис перевіряється в Е1 за документацією хоста [П] | Агент-реалізатор не прочитає H, навіть якщо копія випадково з'явиться в робочій теці |
| Репо: коміти | PR-перевірка (як T41) блокує шляхи `holdout/` і будь-який файл, hash якого є в `holdout.lock.json` | Вміст H не потрапить у git |
| Прогін | Автор розшифровує H у тимчасову теку поза репо, запускає прогін, видаляє теку; у репо — лише агреговані метрики | Поелементні результати не потрапляють до агента |
| Брифи | Бриф кроку 4 і чатів Е1 прямо забороняє читати `research-harness-spec/holdout/` | Додатковий, не основний захист |

Перевірка захисту — тест T41 доповнено кейсом «спроба закомітити файл із `holdout.lock.json`».

## 5. Еталонна розмітка

### 5.1. Схема розмітки claim (F2, F4)

| Поле | Значення |
|---|---|
| `claim_id` | Стабільний ID |
| `span` | Точне місце в тестовому рукописі (розділ, абзац, символи) |
| `material` | true / false — чи це твердження, яке має бути перевірене |
| `criticality` | critical / major / minor |
| `expected_verdict` | `supported` / `partial` / `insufficient` / `contradicted` / `not_found` / `unverifiable` |
| `source_id`, `locator` | Джерело і сторінка / таблиця / абзац, що вирішує вердикт |
| `access_level` | fulltext / abstract / metadata |
| `defect_id` | D1–D14 або null |
| `rationale` | 1–2 речення: чому такий вердикт |

## 9. Пілот A/B/C (M5)

[С] `08-validation`: A — той самий хост і модель + короткий brief без harness; B — A + harness без окремого reviewer; C — B + reviewer у свіжому контексті, лише якщо B працює.

**Задачі [П]** (3 малі задачі, по 3 повтори):
1. Розділ огляду за F4-W (literature).
2. Відповідь на 5 коментарів рецензента до тестового рукопису F4-W (`respond_to_reviewers`).
3. Концептуальний розділ із визначеннями (conceptual).

**Умови:** фіксований model ID і дата, однаковий бюджет і tools, логування витрат включно з невдалими спробами. Оцінка — автор на перемішаних виходах без позначки варіанта. Метрики: MS, MF, MV, MT, M$, MY.

**Рішення за результатом:** B не кращий за A — спрощуємо harness до шаблонів, provenance і валідаторів; C не кращий за B з урахуванням вартості — прибираємо окремого reviewer [С].

Окремо від A/B/C — пілот на реальному першому кейсі (T16): стаття автора про ШІ у викладанні. Її тексти не потрапляють у W чи H.

**Готовність до дисертації [П].** Автор починає дисертацію одразу після пілоту (ADR-007 rev.2). Тому M5 додатково проганяє повний цикл на F7: intake дисертації → структура → контекстні пакети для 3 підрозділів → критики одиниці, розділу й інтеграційний → export / import .docx. Це перевірка механізму, не якості наукового тексту.
