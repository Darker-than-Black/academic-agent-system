# ADR-009 rev.2 — Власні tuple-based числові валідатори

Статус: прийнято 2026-10-27 (рішення автора, документ 12 §7, 2026-10-27). rev.2 — 2026-10-29 (рішення автора: узгодити milestone з ADR-007 rev.3).

## Контекст
Відтворено false positive у `_verify_numerical` AutoResearchClaw: 95 секунд навчання «підтвердили» 95% accuracy (`evidence/validator-probe.json`). `verified_registry.py` того ж проєкту перевіряє належність числа до множини значень із варіантами ×100 / ÷100 і допуском 1% — той самий клас дефекту.

## Рішення
1. Власне числове твердження перевіряється лише проти конкретного result row за повним tuple: run, dataset, split, condition, metric, unit, aggregation.
2. Перетворення (відсотки, округлення, одиниці) задаються явно: expression, input row IDs, precision policy.
3. Похідні числа мають expression і хеш скрипта; renderer підставляє значення з rows, а не з тексту.
4. Числа з джерел (не власні) перевіряються проти excerpt із locator, а не проти всіх чисел у документі.

## Альтернативи
- **Membership-перевірка (є таке число десь у даних)** — відхилено: доведений false positive.
- **LLM-оцінка відповідності числа** — відхилено як основний механізм: недетермінованість; допустима лише як advisory.

## Наслідки
- Тести T05 і негативні кейси з документа 12 §5 (×100-варіанти, N2) обов'язкові: у **M3** — для аналізу відкритих освітніх даних (fixture F8, `05-eval-base.md` §8), у **M6** — для ML-гілки (F1, F3). (rev.1 помилково вказувала M4; змінено 2026-10-29 відповідно до ADR-007 rev.3.)
- Без tuple число в тексті — finding, а не PASS.
