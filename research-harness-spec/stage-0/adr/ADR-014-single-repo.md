# ADR-014 rev.2 — Репозиторій, робочий простір `Projects/` і PR-only

Статус: прийнято 2026-10-27 (рішення автора, крок 1 Р6, Р7). rev.2 — 2026-10-28 (рішення автора 2026-10-27/28: папки `Назва__ID`, розділення harness і робочого простору для інших користувачів, захист holdout).

## Контекст
Координатор пропонував два репозиторії (harness окремо від статей). Автор обрав один. Ризики одного репо: чужі PDF у git (ліцензії), неопубліковані дані, секрети, змішування ліцензії harness із текстами статей. Автор обрав зміни лише через PR.
Бачення автора (2026-10-27): користувач клонує harness, запускає його в Claude CLI, система створює `Projects/` з папкою для кожної статті й дисертації, назва папки — як у статті. Для інших користувачів робочий простір усередині клону harness конфліктує з оновленням harness через `git pull`.

## Рішення
1. **Для автора** — один приватний репозиторій: `harness/` (CLI, schemas, rule packs, skills, тести, evals) і `Projects/` (робочий простір).
2. **Для інших користувачів** — harness встановлюється як інструмент; робочий простір `Projects/` — окрема тека або власний репозиторій користувача, який ініціалізує `rh init-workspace`. Структура робочого простору однакова в обох випадках.
3. **Структура робочого простору:**
   ```
   Projects/
     _author/                     профіль, publications.bib, style/, corpus/
     <Назва статті>__A-2026-001/
     <Назва дисертації>__T-2026-001/
       structure.yaml  map.md  glossary.md
       manuscript/01 Вступ/  02 Розділ 1. …/1.1 …/  …
       sources/ evidence/ reviews/ assets/ history/ export/
   ```
   ID (`A-YYYY-NNN`, `T-YYYY-NNN`) — ключ усіх внутрішніх посилань; назва — для людини. Недозволені для шляхів символи (`: ? « » / \ * | < > "`) прибираються; назва обрізається приблизно до 60 символів; перейменування — командою (`rh rename`), яка оновлює metadata. Одиниці всередині документа — за ADR-019.
4. У git не потрапляють: повні тексти чужих джерел (зберігаються locator, hash, ліцензія, локальний шлях поза git), дані з прапорцем `private`, секрети, holdout оцінювання. Перевірка — CLI-командою перед PR і в CI, якщо він буде.
5. **Holdout** (`05-eval-base.md` §2): у репо відсутній; лише `evals/holdout.lock.json` з hash. Налаштування хоста забороняють читання `**/holdout/**`; PR-перевірка блокує шляхи `holdout/` і файли з hash із lock-файла.
6. Ліцензія harness явно не поширюється на `Projects/` (окремий файл ліцензійного застереження).
7. Усі зміни — через PR із гілок; мердж — автор; прямих комітів у main немає. Повідомлення комітів і PR містять зміни артефактів і посилання на snapshot / operation ID.

## Альтернативи
- **Два репозиторії для автора** — відхилено автором; переваги (ізоляція ліцензій і приватності) компенсуються правилами п. 4–6.
- **`projects/<stable-id>-<slug>` (rev.1)** — замінено: автор хоче знаходити папку за назвою статті.
- **Робочий простір усередині клону harness для всіх користувачів** — відхилено для інших користувачів: конфлікти при оновленні harness.
- **Прямі коміти агента в робочу гілку** — відхилено автором на користь PR.

## Наслідки
- Потрібен `.gitignore` і локальне сховище для чужих PDF поза деревом git.
- Тест T41 — критерій виходу M3; T45 — M1.
- Якщо репозиторій автора колись стане публічним, `Projects/` треба буде винести — це рішення доведеться переглянути.
